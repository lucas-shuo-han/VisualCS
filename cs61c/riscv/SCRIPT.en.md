## 02-from-c-to-assembly

- `00:06` Let's write one line of C: a = b + c;
- `00:10` But a CPU doesn't understand C. All it can run is strings of 0s and 1s.
- `00:15` Two translation steps sit in between. First the compiler turns C into assembly language...
- `00:22` ...then the assembler turns each assembly instruction into a 32-bit machine instruction.
- `00:27` Assembly maps almost one-to-one onto machine code: it's machine instructions written out as text.
- `00:35` The specification of which instructions a CPU supports and which registers it has is called its instruction set architecture (ISA).
- `00:43` It's a contract between software and hardware: software uses only these instructions, and hardware guarantees to execute them correctly.
- `00:53` x86, ARM and RISC-V are all ISAs. CS61C uses RISC-V: open-source, simple and regular.
- `01:03` RISC means a reduced instruction set: few, regular instructions, so the hardware can be simple and fast.
- `01:10` The RV32I base instruction set has only about 40 instructions, and this series covers most of them.
- `01:18` RISC-V arithmetic works only on registers: a tiny amount of very fast storage inside the CPU.
- `01:25` RV32I has 32 integer registers: x0 through x31.
- `01:31` Each register is 32 bits wide. 32 bits, or 4 bytes, is called a word.
- `01:40` Why only 32? Because smaller is faster.
- `01:43` A register can be read or written within one clock cycle; a memory access is often 100 times slower or more.
- `01:53` One of them, x0, is special: its value is always 0.
- `01:58` Anything written to x0 is silently thrown away.
- `02:02` Sounds wasteful? You'll soon see how handy it is.
- `02:07` In assembly we usually call registers by their other names, the ABI names.
- `02:12` Names starting with t are temporary registers...
- `02:15` those starting with s are saved registers...
- `02:18` and the a registers pass arguments and return values.
- `02:21` ra, sp and a few others have special jobs. We'll cover the rules for all these registers with function calls in Episode 7.
- `02:30` Arithmetic instructions have a rigid format: operation name, destination register, then two source registers.
- `02:38` add rd, rs1, rs2 simply means rd = rs1 + rs2.
- `02:45` For example, say s1 holds 7 and s2 holds 5.
- `02:50` Run add s0, s1, s2: both values go into the adder...
- `02:55` ...and the result, 12, is written to s0.
- `02:59` sub works the same way: rd = rs1 − rs2. Order matters: rs2 is subtracted from rs1.
- `03:09` Now let's compile something a bit bigger: a = b + c - d.
- `03:14` Suppose the compiler has put a, b, c and d in s0, s1, s2 and s3.
- `03:22` Each instruction does only one operation, so this takes two steps, with the intermediate result in the temporary register t0.
- `03:30` Let b = 10, c = 20, d = 5. Step one: t0 = 10 + 20 = 30.
- `03:39` Step two: s0 = t0 − d = 30 − 5 = 25. Done!
- `03:48` What if we're adding a constant, as in a = b + 5?
- `03:52` Use addi. The i stands for immediate: the constant is encoded right in the instruction.
- `03:58` RISC-V has no subi: subtracting a constant is just adding a negative one.
- `04:03` addi's immediate is only 12 bits, so it ranges from −2048 to 2047. Why 12 bits? Episode 9 explains.
- `04:14` Now for x0's trick. The assembler offers pseudoinstructions, which it replaces with real instructions.
- `04:21` mv adds 0; li starts from x0 and adds a constant...
- `04:25` ...and nop writes its result to x0, so nothing changes.
- `04:29` One register that's always 0 saves several dedicated instructions. That's RISC thinking.

## 03-memory-lw-sw

- `00:06` There are only 32 registers, but programs have arrays, structs, thousands of variables. Whatever doesn't fit in registers goes in memory.
- `00:15` RISC-V is a load-store architecture: arithmetic works only on registers, and memory is accessed only through dedicated instructions.
- `00:24` A load copies data from memory into a register; a store writes a register's value to memory.
- `00:31` Think of memory as one huge array of bytes: every byte has its own number, its address.
- `00:37` To keep it readable we draw 4 bytes per row: the first row is 0x100 to 0x103, and the next starts at 0x104.
- `00:47` A word takes 4 bytes, so the addresses of neighboring words differ by 4, not 1.
- `00:53` Word addresses are usually multiples of 4; we say they're aligned. A misaligned access may be slower, or even fail outright.
- `01:03` How does a 32-bit number fit into 4 bytes? Take 0x12345678.
- `01:10` RISC-V is normally little-endian: the least significant byte goes at the lowest address.
- `01:16` So reading up from 0x100, the bytes are 78, 56, 34, 12, as if stored backwards.
- `01:25` Luckily, when you load or store a whole word, the hardware puts the number back together, so most of the time you needn't worry about byte order.
- `01:35` Now suppose memory holds an int array A, starting at address 0x100, one word per element.
- `01:42` The array's starting address, its base address, is in s0.
- `01:47` lw means load word. lw t0, 8(s0) loads the word at address s0 + 8 into t0.
- `01:56` The offset 8 plus the base address gives 0x108: exactly where A[2] lives.
- `02:04` So A[i] in C is at byte offset 4 × i.
- `02:08` For A[3] the offset is 12, not 3. This is one of the most common mistakes in assembly.
- `02:15` sw means store word and goes the other way: it writes a register's value to memory. Let's work through a full example.
- `02:23` A[3] = h + A[1], with h in s1. First, load A[1]...
- `02:30` ...then add h: t0 = 10 + 12 = 22...
- `02:35` ...and finally sw stores it to A[3]. Note that sw puts the source register first and the memory address second.
- `02:43` 22 is 0x16 in hex; stored little-endian at 0x10C, that's 16 00 00 00.
- `02:52` Besides whole words, you can also load or store a single byte: lb, lbu and sb.
- `02:59` lb loads this byte into a 32-bit register. So what goes in the other 24 bits?
- `03:05` lb sign-extends: it copies the top bit, the sign bit, into all the upper bits. The top bit of 0xF3 is 1...
- `03:14` ...so the upper 24 bits are all 1s, giving 0xFFFFFFF3. As a signed byte, 0xF3 is −13, and after extension it's still −13.
- `03:27` lbu is the unsigned version: it always fills the upper bits with 0, giving 243.
- `03:34` sb stores just the register's lowest 8 bits to memory; the upper 24 bits are simply ignored.
- `03:42` Half-words (16 bits) follow the same rules: lh, lhu, sh.
- `03:48` In RV32, lw already fills all 32 bits, so there's nothing to extend, and no lwu.

## 04-assembly-in-practice

- `00:06` This episode is practice: we'll translate real C code into RISC-V assembly by hand.
- `00:14` First, assembly vs. C. One: C variables have types; registers don't. They just hold 32 bits.
- `00:21` Two: in C, the type decides the operation. Assembly flips this: the instruction decides how to read the bits.
- `00:29` Say t0 is all ones: as a signed number it's −1, as unsigned it's 4294967295. It depends on the instruction.
- `00:41` Three: C operators have several meanings. On line 2, + is pointer arithmetic; on line 4 it's integer addition, and the two *s are multiplication and dereference.
- `00:53` In assembly, each op name means exactly one operation, and you count the bytes yourself: p + 2 moves 8 bytes, so addi adds 8.
- `01:03` Four: a C statement can hold many operations, but each assembly line is one instruction. This line takes about six.
- `01:12` Assembly has no variable names either, so comments matter: everything from # to the end of the line is a comment. There are no multi-line comments.
- `01:22` Warm-up: f = (g + h) - (i + j), with g through j in x20 through x23, and f in x19.
- `01:33` Approach A follows C: sum each parenthesis into a temporary, x5 or x6, then subtract to get 23. But their old values are lost.
- `01:44` Approach B starts from the same values and uses algebra: compute g + h, then subtract i and j in turn.
- `01:51` Also 23, and x5 and x6 are untouched. The price is algebraic rewriting: harder expressions (say, distributing a multiply) need a smarter compiler.
- `02:04` There are only 32 registers, but that doesn't limit your variables: whatever doesn't fit spills over to memory.
- `02:11` The processor reaches memory through addresses. Directions are processor-centric: reading in is load from, writing out is store to.
- `02:21` RISC-V is a load-store architecture that computes only on registers: data in memory is loaded first, and stored back afterward if needed.
- `02:30` x86 lets one operand come straight from memory, so a single add does it; RISC-V splits it into lw and add.
- `02:39` Base + offset is modeled on arrays and structs: the base points to the start, and the offset is a fixed byte distance, known at assembly time.
- `02:49` Today's big example: four local variables, two of them arrays. We may use only t0, t1, t2 and the stack pointer sp, plus any memory.
- `03:00` sp is x2, which by convention points to the stack of locals. Use x2 as a temporary, and every sp-based access breaks.
- `03:10` We, the human compiler, decide where variables go; we just have to be consistent. On the left: offsets from sp.
- `03:18` a goes at 0(sp); b is "string" plus its terminating \0, 7 bytes starting at 4(sp).
- `03:27` c is 10 ints, 40 bytes, from 12(sp) to 51(sp); d is a single byte at 52(sp).
- `03:36` c starts at 12(sp), not 11(sp), so every int is aligned to a multiple of 4.
- `03:45` Line 1, a = 5: sw can only store a register, so li first puts 5 into t0, then we store it at 0(sp).
- `03:55` Line 2 stores "string"; ASCII gives these 7 bytes. Simplest is li and sb per byte, with \0 straight from x0: 13 instructions.
- `04:06` Smarter: pack 4 characters into a word and store it with one sw. In little-endian the first character must be the lowest byte, so "stri" becomes 0x69727473.
- `04:20` After sw to 4(sp), reading from low to high addresses gives s, t, r, i.
- `04:28` The remaining n, g, \0 plus one zero byte make 0x0000676E, stored at 8(sp). Just 4 instructions in total.
- `04:40` A constant this big won't fit addi's 12-bit immediate, so li expands into lui + addi. More in Episode 12.
- `04:48` Line 3, int c[10], has no initializer, so no instructions. The layout itself generates none either.
- `04:56` Line 4, d = b[3]: b starts at 4(sp), and b[3] is 3 bytes further, at 7(sp).
- `05:06` lb reads 0x69, which is 'i'. Its top bit is 0, so sign extension fills in 0s. Then sb stores it at 52(sp): that's d.
- `05:17` Line 5, c[4] = a+d: both values must be loaded first. a is an int, so lw; d is an unsigned uint8_t, so lbu.
- `05:29` 5 + 105 = 110. c starts at 12(sp) and c[4] is 4 × 4 bytes further, so we store at 28(sp).
- `05:40` The last line, c[a] = 20, is the hardest. Can we use a fixed offset, as for c[4]?
- `05:47` No: a is a variable, only known to be 5 at runtime, but the offset is fixed at assembly time. The address must be computed in a register.
- `05:56` The address of c[a] is sp + 12 + 4 × a. First put 20 in t0, then load a into t1.
- `06:05` Multiplying by 4 is a left shift by 2: slli turns 0b101 into 0b10100, which is 20. Shifts are covered in Episode 5.
- `06:17` Adding c's offset, 12, gives 32, or 0x20; adding sp's 0x1000 gives the full address 0x1020.
- `06:29` The address is complete, so the offset is 0: sw t0, 0(t1) writes 20 into c[5].
- `06:38` Quick check: what's in t1 now? Not the value of c[a], but its address, &c[a].
- `06:45` Two short exercises. First: x5 = 0x100. After these three instructions, what's in x12?
- `06:53` li sets x11 to 0x000093F5; sw stores it at 0x100 in little-endian order: F5 93 00 00.
- `07:06` lb x12, 1(x5) reads the byte at 0x101: 0x93, not 0xF5.
- `07:14` 0x93 is 1001 0011, so its top bit is 1. lb sign-extends, filling the upper 24 bits with 1s.
- `07:25` So x12 = 0xFFFFFF93. Two traps: little-endian puts 0x93 at 1(x5), and lb extends it into a negative number.
- `07:38` Second: x and y are int pointers, held in x3 and x5. Which instructions implement *x = *y?
- `07:46` 1 and 2 copy the pointers themselves; 3 and 4 use lw to overwrite a pointer register. None of them work.
- `07:54` The answer is 5 → 6: lw loads *y into the free x8, then sw writes it where x points. Memory to memory must go through a register.
- `08:05` Order matters: 6 → 5 would store x8's old value first. 7 and 8 treat x8 as an address, also wrong.
- `08:15` Two last details. First: there is lbu, so why no "sbu"? Look at what a store does.
- `08:21` sb takes only the lowest byte and puts it in memory as is; nothing to extend. A load, though, must fill all 32 bits of the register.
- `08:31` A register is just bits, and there's no telling how later instructions will use it, so the upper bits must be defined: sign-extend or fill with 0s.
- `08:42` Second, alignment: the spec guarantees that loads and stores at a multiple of the access size never raise a misaligned exception.
- `08:50` Misaligned access is up to the implementation: it may be slow, or fail. So treat "should be aligned" as "must be aligned".
- `08:59` Also, the spec allows both little-endian and big-endian implementations; CS61C uses little-endian.

## 05-decisions-and-loops

- `00:06` A program is a sequence of instructions in memory. A special register, the program counter (PC), holds the address of the current instruction.
- `00:15` Each instruction is 4 bytes long. After each one, the PC goes up by 4 to point at the next.
- `00:22` But if we could only run one instruction after another, we could never write an if or a loop. We need instructions that jump.
- `00:30` The conditional branch beq (branch if equal): if rs1 equals rs2, jump to Label; otherwise carry on with the next instruction.
- `00:40` RISC-V has six conditional branches: equal, not equal, less than, greater or equal, plus unsigned versions of the last two.
- `00:49` No bgt or ble? Swap the operands, since a > b means b < a. The assembler also provides them as pseudo-instructions.
- `01:01` There's also an unconditional jump, j Label: it always jumps. It's shorthand for jal x0, Label; Episode 7 covers jal.
- `01:12` A label is just a name for a place in the code; the assembler converts it into an address.
- `01:19` Let's translate an if-else. The variables f, g, h, i, j live in s0 through s4.
- `01:27` The key trick: negate the condition. C runs the then-part when i == j, so the assembly uses bne instead, skipping straight to Else when they differ.
- `01:38` Case 1: i equals j. bne doesn't branch, so we run the add…
- `01:44` …then j Exit skips over the else part.
- `01:48` Case 2: i doesn't equal j. bne jumps straight to Else, runs the sub, and simply falls through to Exit.
- `01:56` Don't leave out j Exit: without it, the program would finish the then-part and fall right through into the else part.
- `02:04` Before writing loops, let's meet a few bitwise instructions. They work on 32-bit values bit by bit.
- `02:11` and: a result bit is 1 only if both bits are 1. It's often used as a mask, keeping just the bits you want.
- `02:19` or: the result is 1 if either bit is 1…
- `02:22` …xor: the result is 1 only if the two bits differ.
- `02:27` Each has an immediate version: andi, ori, xori. For example, andi t0, t1, 0xFF extracts the lowest byte.
- `02:37` There's no real not instruction: -1 is all 1s, so xor with -1 flips every bit. The not pseudo-instruction does just that.
- `02:48` Shifts slide all the bits over together. sll is shift left logical: move left, filling the right with 0s.
- `02:56` Shifting left by k multiplies by 2^k: 22 shifted left by 2 becomes 88.
- `03:04` There are two right shifts. srl, shift right logical, fills the left with 0s.
- `03:10` sra, shift right arithmetic, fills the left with the sign bit, so a negative number divided by a power of 2 stays negative.
- `03:19` Now let's put it all together: add up the n elements of an array A.
- `03:24` A's address is in a0 and n is in a1; i lives in t0 and sum in s1.
- `03:31` The skeleton of a loop: at the top, test the condition and exit if it fails; at the end of the body, jump back to the top.
- `03:39` Once again the condition is negated: C keeps going while i < n, so the assembly exits when i >= n.
- `03:48` A[i] is at address A + 4i: slli by 2 computes 4i, then we add the base address.
- `03:56` First pass: i = 0. The bge isn't taken; we compute address 0x100, load A[0] = 3, and sum becomes 3.
- `04:07` Every pass after that is the same: compute A + 4i, load A[i] and add it to sum, then increment i…
- `04:15` When i reaches 4, the bge condition holds and we jump to Done. sum = 3 + 1 + 4 + 1 = 9.

## 06-control-flow-patterns

- `00:06` Before a program runs, it's loaded into the text segment of memory: each instruction is a 32-bit word, 4 bytes, one right after another.
- `00:15` The processor consists of a control unit and a datapath. The datapath holds the 32 registers, x0–x31.
- `00:24` The PC sits in the datapath too, holding the current instruction's address. It's a register, but not one of x0–x31, and instructions rarely read or write it explicitly.
- `00:36` The control unit repeats four steps forever: read the PC, fetch the instruction from memory, execute it, and update the PC.
- `00:45` Let's walk through the example from the course notes. Step 1: read the PC, which holds 0x00000008.
- `00:54` Step 2: fetch the instruction at that address. In memory it's just a 32-bit number: 0x01051613.
- `01:04` The control unit decodes it as slli x12 x10 0x10. Like the notes, this episode leaves out the commas between operands. Episode 9 covers the encoding.
- `01:17` Step 3: execute. x10 is 0x000034FF; shifted left by 0x10 (that is, 16) bits, it puts 0x34FF0000 in x12.
- `01:32` Step 4: update the PC. Every instruction is 4 bytes, so by default the PC goes up by 4, to 0x0000000C: the next instruction.
- `01:44` So this arithmetic instruction actually changes two registers: the destination register x12, and the PC.
- `01:51` Branches and jumps instead set the PC to a label's address in step 4 (a conditional branch only when its condition holds).
- `02:00` Those 5 words in memory are these 4 lines of assembly, which happen to be a practice problem from the notes.
- `02:07` 0x34FF doesn't fit in a 12-bit immediate, so li expands into two instructions (more in Episode 12). That's why slli is at 0x08.
- `02:17` Question: after these 4 lines run, what's in x12? Pause and think it through.
- `02:25` After the first line, x10 = 0x000034FF. Here are all 32 bits; each group of 4 bits is one hex digit.
- `02:36` slli shifts left by 16, filling in 0s on the right: x12 = 0x34FF0000, just as the processor computed earlier.
- `02:47` srli shifts right by 8, filling in 0s on the left: x12 = 0x0034FF00. The top bit was 0, so srai would give the same result.
- `03:01` Finally, and works bit by bit: a result bit is 1 only where both inputs have a 1.
- `03:07` Only 3 columns have 1s in both rows, so x12 = 0x00003400. The answer is B.
- `03:17` A branch compares and then jumps. But sometimes we just want the result of the comparison, like lt = (a < b) in C: 1 if true, 0 if false.
- `03:29` The instruction for this is slt, set less than: it sets rd to 1 if rs1 < rs2, and to 0 otherwise.
- `03:38` With a and b in x5 and x6 and the result in x7: slt x7 x5 x6. 3 < 5 is true, so x7 = 1.
- `03:50` sltu is the unsigned version (u for unsigned). When do the two give different answers? Here's an example.
- `03:58` x5 = 0xFFFFFFFF: all 32 bits are 1. As a signed number it's −1; as an unsigned number it's 4294967295.
- `04:12` slt compares −1 < 1: true, so 1. sltu compares 4294967295 < 1: false, so 0.
- `04:25` In C, a variable's declaration determines its type. In assembly, bits have no type: the instruction decides whether they're signed or unsigned.
- `04:35` The immediate versions, slti and sltiu, compare a register with a constant. Same x5: slti x7 x5 10 gives 1, sltiu gives 0.
- `04:49` By the way, multiplication (mul) isn't in the RV32I base instruction set. It belongs to the M extension.
- `04:58` General multiplication needs far more complex circuitry than shifting, so the base set leaves it out. Division and remainder are in M too; floating point is in F.
- `05:10` Back to branches. First, an if-else, with the variables x, y, z, i, j in x10 through x14.
- `05:19` There are two ways to translate it. Choice B is what we did in Episode 5: negate the condition with bne.
- `05:26` Choice A keeps the condition: beq jumps to If when they're equal, so the else part comes first. Both are correct, and both take 4 instructions.
- `05:36` What if there's no else?
- `05:38` Choice A uses beq: if equal, jump to If and run the add; if not, it still needs j End to skip over the add.
- `05:47` Choice B uses bne: if not equal, jump straight to End; if equal, fall through to the add.
- `05:55` Both work. But B mirrors the structure of the C code and needs only 2 instructions, one fewer than A, so it performs better too.
- `06:04` Assembly has no while or for, only branches and jumps. They're like C's goto: execution continues at some label.
- `06:12` Don't use goto in real C code: it makes programs hard to read (xkcd 292 warns it attracts velociraptors). But it's a great intermediate step for translation.
- `06:24` The recipe: rewrite the control structure with goto, then turn it into instructions line by line. To get real instructions, let cond be x5 < x6.
- `06:36` The if we just saw works this way: if (!cond) goto AfterIf. When the condition fails, we skip the then-part.
- `06:43` while: test at the top and exit if the condition fails; goto Loop at the bottom jumps back. Episode 5's loop had exactly this shape.
- `06:52` A break is just a goto to the code after the loop, which becomes a single j.
- `06:58` Turn a for into a while first: move the initialization, startline, before the loop, and the increment, incline, to the end of the body…
- `07:07` …then translate it like any while loop.
- `07:10` do-while runs the body first and tests at the end, jumping back to Loop if the condition holds. No negation, and no j.
- `07:19` Finally, a complete example: add up the 20 elements of the int array arr.

## 07-function-calls

- `00:06` Calling a function takes six basic steps.
- `00:09` First, put the arguments where the function can find them, then jump there…
- `00:13` …the function sets up its own local storage and runs its body…
- `00:17` …puts the return value in place, and finally jumps back to where it was called.
- `00:23` Here's the simplest example: a = sum(a, b), with a in s0 and b in s1.
- `00:31` Step one: put the arguments in a0 and a1. The return value will come back in a0, too.
- `00:38` jal means jump and link: it saves the address of the next instruction, PC + 4, in ra, then jumps to sum.
- `00:48` The function computes its result into a0…
- `00:51` …then jr ra jumps back to the address saved in ra, 0x100C, and execution carries on.
- `00:59` Why not just j back? Because sum may be called from many places; only ra knows where to return this time.
- `01:06` jr ra is shorthand for jalr x0, 0(ra), and is often written as ret.
- `01:14` Here's the catch: there's only one set of registers, shared by the caller and the callee.
- `01:20` But f needs registers too. If it overwrites a value the caller still needs, that data is silently clobbered.
- `01:27` So everyone agrees on a set of rules, called the calling convention.
- `01:32` The t and a registers and ra are caller-saved: the callee may change them freely. If the caller needs them afterward, it must save them itself.
- `01:41` The s registers and sp are callee-saved: a function that uses one must save the old value first and restore it before returning.
- `01:49` In other words: across a function call, the s registers are guaranteed to keep their values; the t and a registers are not.
- `01:57` So where do these old values go? Into a region of memory called the stack.
- `02:03` A program's memory is split into a few regions: code, static data, the heap, and, up at the high addresses, the stack.
- `02:12` The stack grows down, from high addresses toward low ones. sp, the stack pointer, points to the top of the stack: the lowest address in use.
- `02:23` Let's zoom in. Suppose a function needs to save two registers, ra and s0.
- `02:29` To push, first subtract 8 from sp to make room for two words…
- `02:33` …then store the registers with sw: ra at sp + 4, s0 at sp + 0.
- `02:41` Now the function is free to change ra and s0.
- `02:45` Before returning, pop in reverse order: lw brings back the old values, then sp is moved back up.
- `02:53` sp is back where it started, and the registers hold their old values. The saved data isn't erased; it just no longer belongs to anyone.
- `03:03` Finally, a complete example: sumSquare calls another function, mult.
- `03:08` On entry, x = 3 is in a0, y = 5 is in a1, and ra holds the caller's return address.
- `03:17` sumSquare itself calls mult with jal, and jal overwrites ra. Without saving ra first, it could never get back to its caller.
- `03:26` y must go on the stack too: a1 is about to carry x, and since the a registers are caller-saved, mult may change a1 as well.
- `03:35` First comes the prologue: make room for two words, then save ra and y.
- `03:40` Set up the arguments for mult(3, 3), then jal: ra now holds the address of the instruction after the jal, here 0x2014.
- `03:52` After mult returns, there's no telling what's in a1. Luckily, y is safe on the stack.
- `03:58` That gives 9 + 5 = 14. Then the epilogue: restore ra, add 8 back to sp, and jr ra returns to the caller.
- `04:08` The prologue saves the state; the epilogue restores it. Almost every function that calls another has this shape.

## 08-recursion-and-stack-frames

- `00:06` Episode 7 used jal and jr ra. In fact, RISC-V has only two real unconditional jump instructions.
- `00:15` jal rd, label stands for "jump and link," but it really links first: it writes PC + 4 into rd, then jumps to label.
- `00:25` jalr rd, rs1, imm also links first, but jumps to rs1 + imm: the address comes from a register.
- `00:34` Every other jump is a pseudoinstruction: j, jr and ret write the link to x0, discarding it; jal without rd links to ra.
- `00:46` Why two? jal's target is fixed at assembly time, which is just right for calling a function by name.
- `00:52` jalr's target comes from a register at run time. That covers returning to the address in ra, calling through a function pointer, and, with auipc, jumping far.
- `01:05` This episode's star is factorial, defined by factorial(1) = 1 and factorial(n) = n × factorial(n − 1).
- `01:16` What if we save nothing? Say main calls factorial(2): a0 = 2, and ra holds the way back to main.
- `01:23` factorial(2) puts the argument 1 in a0 and does a jal: now ra points back into factorial(2).
- `01:32` factorial(1) returns 1, but factorial(2)'s 2 was overwritten by the argument 1; and ra still points into factorial(2), so it can never get back to main.
- `01:44` The lazy fix: on every call, push all of x1 through x31, then load them all back afterward.
- `01:52` But memory is slow, and a call usually needs to protect only a few registers.
- `01:58` The fix is Episode 7's calling convention: callers can rely only on s registers and sp; a callee that uses an s register saves it first and restores it before returning.
- `02:09` A recursive function plays both roles: callee to the level above, caller to the level below.
- `02:16` Here is the notes' factorial, which follows the calling convention, starting at address 0x2000. First, spot the prologue and epilogue.
- `02:26` The prologue carves out 8 bytes on the stack: this call's stack frame. The jal further down will overwrite ra, and s0 is borrowed, so its old value is saved too.
- `02:38` mv s0 a0 copies n into s0. s registers survive calls, so n is still there when the recursive call returns.
- `02:47` bne compares two registers, so li first puts 1 in t0. If n ≠ 1, branch to recurse.
- `02:56` Otherwise it's the base case: a0 = 1. It can't just jr ra: s0 isn't restored and the frame isn't popped yet, so it jumps to the epilogue.
- `03:07` recurse: a0 = n − 1, and it calls itself. On return a0 = (n − 1)!, which is multiplied by n from s0.
- `03:19` The epilogue runs in the opposite order: load ra and s0 back from the stack, then add 8 to sp to pop the frame, and finally jr ra.
- `03:30` Let's trace factorial(3) all the way through. main has already allocated a 12-byte frame, so sp = 0xFFFFFFD4.
- `03:41` main puts 3 in a0 and executes the jal at 0x1004: ra = 0x1008, and control enters factorial.
- `03:52` factorial(3)'s prologue: sp drops by 8 to 0xFFFFFFCC, then it saves ra = 0x1008 and main's s0 = 42.
- `04:05` mv sets s0 = 3. Since 3 ≠ 1, it branches to recurse: a0 = 2, and the jal at 0x2024 sets ra = 0x2028.
- `04:19` factorial(2) pushes a frame the same way: sp = 0xFFFFFFC4, saving ra = 0x2028 and s0 = 3, then calls itself with a0 = 1.
- `04:35` factorial(1) pushes one too: sp = 0xFFFFFFBC, saving ra = 0x2028 and s0 = 2.
- `04:47` Each of the three frames holds its own ra and s0. factorial(3)'s ra leads back to main; the other two lead to the mul at 0x2028.
- `04:59` factorial(1) is the base case: a0 = 1, then j to the epilogue.
- `05:06` The epilogue restores ra = 0x2028 and s0 = 2, sp goes back to 0xFFFFFFC4, and jr ra returns to the mul.
- `05:18` a0 = s0 × a0 = 2 × 1 = 2. The 2 in s0 is factorial(2)'s own n: factorial(1) used s0, but restored it before returning.
- `05:34` factorial(2) runs its epilogue: ra = 0x2028, s0 = 3, sp = 0xFFFFFFCC. Back at the mul: a0 = 3 × 2 = 6.
- `05:50` factorial(3) restores ra = 0x1008 and main's s0 = 42, sp goes back to 0xFFFFFFD4, and it returns to main.
- `06:03` Back in main: a0 = 6, and sp and s0 are just as they were before the call. The popped frames are still in memory; nobody uses them anymore.
- `06:15` The notes' foo is recursive too: foo(i) = i + foo(i − 1). Put it next to factorial and the skeleton is identical.
- `06:25` Only three things differ: it compares against x0 directly, saving an li; the base case returns 0; and multiply becomes add.
- `06:34` The notes' main keeps foo(3) in s0, where it survives the call to foo(100). At its deepest, foo(100) has 101 frames on the stack: 808 bytes.
- `06:49` Not every function needs the stack. In the notes, sum_square calls mult twice, and mult calls nothing at all.
- `06:56` A function like mult is a leaf function: with no jal, ra is never overwritten, and if it uses only t and a registers, it needs no sw or lw at all.
- `07:09` Here's the full register convention table. gp and tp have special jobs outside the calling convention, so leave them alone.
- `07:17` s0 is also called fp, the frame pointer: sp may move partway through a function, but fp keeps pointing at the current frame.
- `07:27` The notes' func_a moves sp partway through: it calls func_b and needs t1 both before and after the call.
- `07:34` The prologue pushes 8 bytes and saves ra and s0. ra is caller-saved, but by convention it is saved in the prologue anyway.
- `07:43` t1 = 10, s0 = 20. t1 is caller-saved and func_b may change it, so before the call, func_a pushes 4 more bytes to save t1.
- `07:55` After func_b returns, t1 could hold anything. Luckily the stack has a copy: t1 = 10 comes back, and those 4 bytes are popped right away.
- `08:05` When sp moves, the offsets move with it: a moment ago 0(sp) was t1; only after the pop is it ra again.
- `08:13` Finally t1 = 15 and s0 = 25. The epilogue restores ra and the caller's s0 = 42, puts sp back, and ret returns.
- `08:27` Three true-or-false questions from the notes' exercises. Think them over first.
- `08:33` 1 is false: a0 and a1 carry return values back. Like the t registers, the a registers are caller-saved.
- `08:41` 2 is true: s registers are callee-saved, usually saved in the prologue and restored in the epilogue.
- `08:48` 3 is false: func_a pushed t1 partway through. As long as every push has a matching pop, the stack can be used anywhere.
- `08:57` Finally, Episode 7's six steps once more. Steps 1 and 2 belong to the caller: save any t and a registers it still needs, set up the arguments, then jal.
- `09:09` Step 3, the prologue: lower sp once, making room for local arrays too; save the s registers it uses, and ra if it calls others.
- `09:19` Step 4 is the body. Steps 5 and 6 are the epilogue: return value in a0, restore registers, pop the frame, jr ra.
- `09:29` The notes' analogy: a call is like house-sitting for your parents. They're the caller, you're the callee; the table is the registers, the closet is memory.
- `09:39` The arguments are the essentials on the table. Stash the rest in the closet (prologue); before leaving, put it back and leave a gift: the return value (epilogue).

## 09-formats-r-i-s

- `00:06` So far we've been writing assembly. But what the hardware actually runs is a sequence of 32-bit binary numbers.
- `00:13` Instructions are data too, kept in memory just like any other data: that's the stored-program idea.
- `00:19` The PC holds the memory address of the current instruction.
- `00:23` So how exactly does a line of assembly become 32 bits?
- `00:28` The 32 bits are cut into pieces called fields. Instructions whose operands are all registers, like add and sub, use the R-type format.
- `00:37` rd, rs1 and rs2 get 5 bits each: 2 to the 5th is 32, just enough to number all 32 registers.
- `00:47` The opcode, in the lowest 7 bits, says what kind of instruction this is; funct3 and funct7 pin down the exact operation.
- `00:56` Let's encode add x18, x19, x10.
- `01:00` rd = 18 is 10010 in 5-bit binary; rs1 = 19 is 10011; rs2 = 10 is 01010.
- `01:13` For add, funct3 and funct7 are both 0, and the opcode for R-type arithmetic is 0110011.
- `01:22` Every 4 bits make one hex digit: the whole instruction is 0x00A98933.
- `01:29` What about sub? Only funct7 changes, to 0100000. That 1 in bit 30 tells the hardware to make the adder subtract.
- `01:40` All R-type operations share one opcode; the combination of funct3 and funct7 tells them apart.
- `01:48` addi has only two registers, plus a constant. Where does the constant go?
- `01:53` I-type merges R-type's funct7 and rs2 slots into one 12-bit immediate; every other field stays exactly where it was.
- `02:02` That answers the question from Episode 2: the immediate only gets these 12 bits, and 12-bit two's complement spans exactly −2048 to 2047.
- `02:14` Encode addi x15, x1, -50: -50 in 12-bit two's complement is 1111 1100 1110.
- `02:26` When it runs, the hardware sign-extends these 12 bits to 32 and adds them to rs1. The encoding is 0xFCE08793.
- `02:38` Loads are I-type too. In lw x14, 8(x2), the offset 8 is the immediate and the base register x2 goes in rs1.
- `02:49` All loads share one opcode; funct3 picks the width and signedness: lb, lh, lw, lbu, lhu.
- `02:59` slli, srli and srai are I-type too, but a shift amount is at most 31, so only the immediate's low 5 bits are used.
- `03:10` A store has two source registers, the data and the base, and no destination, but it still needs a 12-bit offset.
- `03:18` S-type's trick: split the immediate in two. The upper 7 bits go where funct7 was, the lower 5 where rd used to be.
- `03:26` Encode sw x14, 8(x2). The offset 8 in 12 bits is 0000000 01000: the upper 7 bits are all 0, the lower 5 are 01000.
- `03:42` The data to store, x14, goes in rs2 and the base x2 in rs1; funct3 = 010 means a full word, and the opcode is 0100011.
- `03:55` Put together, this sw is 0x00E12423.
- `04:02` Stack the three formats: why does S-type split its immediate so awkwardly?
- `04:08` The answer: in every format that uses them, rs1 and rs2 sit in the same place.
- `04:14` The same goes for funct3 and opcode. The hardware can read the registers from fixed positions before it even knows the instruction type.
- `04:22` Register reads and decoding can happen at the same time: simpler, faster circuits. A lovely touch in RISC-V's design.

## 10-reading-machine-code

- `00:06` As Episode 2 showed, x86, ARM and RISC-V are three different ISAs. Hand the same line of C to three compilers…
- `00:15` …and the machine code comes out completely different. Most phones run ARM chips; most PCs run x86.
- `00:22` Even the lengths differ: x86 instructions vary in size, and this one is just 2 bytes.
- `00:29` RISC-V instructions are always 32 bits, as wide as a data word, so instructions and data can share memory hardware.
- `00:38` So a program binary is tied to its ISA: a RISC-V executable simply won't run on an Intel x86 machine.
- `00:46` ISAs are often backward compatible, though: today's x86 processors still run programs written for the Intel 8088 in 1981.
- `00:57` Last episode, assembly became machine code. Now the reverse: how do we read machine code back as assembly? That's disassembly.
- `01:05` Let's practice on this word: 0x01B342B3.
- `01:11` Step one: convert to binary. Each hex digit expands to exactly 4 bits.
- `01:16` Next, find the opcode: whatever the format, it always sits in the lowest 7 bits.
- `01:22` Each format has its own set of opcodes. Look it up: 0110011 means R-type.
- `01:29` Step two: only the format tells us how to cut the other 25 bits. For R-type: funct7, rs2, rs1, funct3, rd.
- `01:41` Step three: funct3 = 100 and funct7 = 0000000. Look them up in the R-type table: it's xor.
- `01:52` Note that the mnemonic xor isn't stored in any single field: opcode, funct3 and funct7 decide it together.
- `02:00` Step four: each register field is a 5-bit unsigned number. rd = 00101 = 5, rs1 = 00110 = 6, rs2 = 11011 = 27.
- `02:17` Then convert to register names: x5 is t0, x6 is t1, x27 is s11.
- `02:25` Put it together: xor t0, t1, s11.
- `02:30` Watch the order: assembly lists rd, rs1, rs2, but the fields run rs2, rs1, rd from left to right, exactly reversed.
- `02:42` That's all four steps. The first two work the same for every format; the last two depend on it.
- `02:49` Back to the full R-type table: all 10 instructions share one opcode, but there are only 8 funct3 values.
- `02:57` Two pairs share a funct3: add and sub are both 000; srl and sra are both 101.
- `03:06` It's funct7 that tells them apart. It takes only two values, and they differ in a single bit: bit 30.
- `03:13` That's 17 bits just to pick the operation, far more than needed. But keeping the fields aligned matters more than saving bits.
- `03:21` Take add t0, t1, s11: flip bit 30 from 0 to 1 and it becomes sub t0, t1, s11.
- `03:31` add and sub share one adder, and bit 30 is a flag: when it's 1, rs2 is negated (invert the bits, add one) before the addition.
- `03:41` With funct3 = 101 it's a right shift. Bit 30 = 0 gives srl, a logical shift: the vacated top bits fill with 0s.
- `03:51` Bit 30 = 1 gives sra, an arithmetic shift that fills with the sign bit. This time the flag controls sign extension.
- `04:00` Immediate shifts use a variant CS61C calls I*-type: shifts go up to 31, so only the low 5 immediate bits are used.
- `04:11` The upper 7 bits aren't part of the number; they act like funct7. For srai they're 0100000, and the flag is bit 30 once again.
- `04:21` Clear bit 30 and you get srli. Left shifts are always logical, so slli always has a 0 there.
- `04:30` I-type is more than addi. Next to R-type, the funct3 codes match: addi and add, xori and xor, slti and slt…
- `04:41` The one gap is subi: to subtract a constant, just addi a negative number.
- `04:46` A 3-bit funct3 has only 8 codes, and they're all used up here; srli and srai even need bit 30 to tell them apart.
- `04:55` The five loads need funct3 codes too, so they get an opcode of their own. All told, I-type has 4 opcodes.
- `05:03` ecall (environment call) asks the operating system for a service, such as printing text or ending the program.
- `05:10` ebreak hands control to the debugger; it's how debuggers implement breakpoints.
- `05:16` Neither takes operands: ecall is all 0s apart from the opcode, and ebreak just adds a 1 in the lowest bit of the immediate.
- `05:26` Loads and stores share funct3 codes too: lb and sb are 000, lh and sh are 001, lw and sw are 010.
- `05:38` lbu and lhu have no store versions: a store writes just the bytes it targets, with nothing to extend. RV32 has no lwu either.
- `05:49` Why are loads and jalr I-type? Both compute rs1 + immediate, an address or a jump target, so they reuse the same adder.
- `05:59` jalr rd, rs1, imm (also written jalr rd, imm(rs1)) saves PC + 4 in rd, then jumps to rs1 + imm.
- `06:12` The ret and jr ra from Episode 7 are pseudo-instructions with no opcode of their own: the assembler turns both into jalr x0, ra, 0.
- `06:24` rd is x0 because a return doesn't need to save a return address: anything written to x0 is discarded.
- `06:32` Encoding: immediate 0, rs1 = ra = x1, rd = x0. There's only one jalr, so funct3 selects nothing; it's just 000.
- `06:46` The opcode is 1100111, giving 0x00008067. Spot this word in a disassembly and you know a function is returning.
- `06:59` One more example, this time S-type: sw x14, 36(x2).
- `07:06` 36 in 12 bits is 0000 0010 0100. The top 7 bits, 0000001, go in imm[11:5]; the low 5 bits, 00100, go in imm[4:0].
- `07:25` Why split it? The funct7 slot alone has 7 bits, only 128 values. With no rd, a store borrows rd's 5 bits to make 12.
- `07:35` The rest is routine: rs2 = x14, rs1 = x2, funct3 = 010 for sw, and opcode 0100011.
- `07:48` The result is 0x02E12223. Disassembling reverses this: glue the two pieces back together, and 0000001 00100 is 36.
- `08:02` To finish, two for you: translate these words into assembly. Pause the video and try them yourself.
- `08:10` Question 1: opcode 0110011 means R-type; funct3 and funct7 are all 0s, so it's add.
- `08:19` rd = 1, rs1 = 2, rs2 = 3: the answer is add x1, x2, x3, that is, add ra, sp, gp.
- `08:32` Question 2: opcode 0000011 is a load, and funct3 = 010 makes it lw; rd = 10 is a0, and rs1 = 2 is sp.
- `08:46` The immediate 1111 1111 1100 has its top bit set, so in two's complement it's −4. Answer: lw a0, -4(sp).

## 11-formats-b-u-j

- `00:06` A conditional branch compares two registers, rs1 and rs2, and needs a target. It writes no register, so there's no rd.
- `00:15` But the target address alone is 32 bits; it can't possibly fit inside a 32-bit instruction. What now?
- `00:22` Observation: branches rarely go far. An if or a loop body is usually a few to a few dozen instructions.
- `00:30` So we encode only the offset from the current PC. This is called PC-relative addressing.
- `00:36` RISC-V leaves room for 16-bit compressed instructions, so instruction addresses are always even: an offset's lowest bit is always 0 and isn't stored.
- `00:47` So 12 bits encode a 13-bit offset: about ±4 KiB, or roughly 1024 instructions in either direction.
- `00:57` A bonus: move the whole block of code elsewhere in memory and not one branch offset changes. That's position-independent code.
- `01:06` B-type is laid out almost like S-type: rs1, rs2, funct3 and opcode stay put, and the immediate is split in two again.
- `01:15` But the immediate's bits are "scrambled": bit 12 goes in the instruction's top bit, and bit 11 moves to the end of the right-hand piece.
- `01:24` That reuses S-type's wiring: bits 10:5 and 4:1 sit exactly where they do in S-type, and the sign bit is still bit 31.
- `01:35` Encode beq x19, x10, End. End is 4 instructions ahead, so the offset is 16 bytes.
- `01:44` 16 in 13-bit binary is 0 0000 0001 0000. Bit 0 is dropped; every other bit goes to its assigned seat.
- `01:54` Registers as usual: rs2 = x10, rs1 = x19. beq's funct3 is 000, and the branch opcode is 1100011.
- `02:08` The final machine code is 0x00A98863.
- `02:13` A 12-bit immediate only holds small constants. How do we get a 32-bit constant like 0xDEADBEEF into a register?
- `02:23` U-type has just rd and a 20-bit immediate. lui (load upper immediate) uses this format.
- `02:30` lui t0, 0xDEADB puts the 20-bit immediate into t0's upper 20 bits and clears the lower 12.
- `02:40` Then just addi the low 12 bits, 0xEEF? Careful: addi's immediate is signed.
- `02:46` 0xEEF has its top bit set, so as 12-bit two's complement it means −273, and it gets sign-extended to 0xFFFFFEEF.
- `02:58` The sum is 0xDEADAEEF: a 1 was "borrowed" from the upper 20 bits.
- `03:05` The fix: when the top bit of the low 12 is set, add 1 to the upper 20 bits first: lui t0, 0xDEADC.
- `03:14` Luckily there's no need to do this by hand: the assembler expands the pseudo-instruction li t0, 0xDEADBEEF into these two.
- `03:26` The other U-type instruction, auipc, shifts its immediate left by 12 and adds it to the PC, to reach addresses far from the current one.
- `03:37` jal needs only rd and an offset, so J-type gives all 20 remaining bits to the immediate.
- `03:44` Again in 2-byte units with bit 0 not stored: a 21-bit offset, about ±1 MiB. That covers the vast majority of function calls.
- `03:55` The bits are scrambled too, lining up as many as possible with I-type and U-type; the sign bit stays at bit 31.
- `04:03` Need to go farther? jalr is I-type: it jumps to rs1 + immediate and saves PC + 4 in rd.
- `04:12` Pair it with auipc for the upper 20 bits and you can reach any 32-bit address. That's how the pseudo-instruction call expands.
- `04:21` Here are all six RV32I formats together.
- `04:25` rs1, rs2, rd and opcode never move; the only thing that changes is how the immediate is laid out.
- `04:33` And the immediate's sign bit is always bit 31, so sign extension can start before the instruction type is even known.

## 12-addressing-and-big-constants

- `00:06` We now have all six instruction formats. This time, a different angle: how does an instruction compute the address it accesses, or the target it jumps to?
- `00:15` These rules are called addressing modes. RISC-V mainly uses three.
- `00:20` First, base/displacement: address = register + immediate. That's how lw and sw find their data.
- `00:28` jalr belongs here too: it jumps to rs1 + immediate. The new PC depends only on a register, not on where the jalr itself sits.
- `00:39` Second, PC-relative addressing: an offset added to the PC. Conditional branches, jal and auipc all use it.
- `00:49` Third, absolute addressing: the full address is given directly. For example, lui loads the address's upper 20 bits, and jalr adds the lower 12 and jumps.
- `01:01` In fact, almost every instruction sets the new PC relative to the current one: PC + 4 for most, PC + offset for branches and jal. Only jalr is different.
- `01:14` The pseudo-instructions fit this map too: j is shorthand for jal x0, so it's PC-relative; jr and ret are shorthand for jalr.
- `01:26` Let's compute some real offsets. Here is the loop from the course notes, with a sample address on each instruction: beq is at 0x0C.
- `01:36` Labels aren't instructions: Loop and End don't exist in machine code at all. The assembler must turn them into PC-relative offsets.
- `01:44` Case 1: the beq isn't taken. The PC moves to the next instruction: offset +4.
- `01:51` Case 2: the beq is taken and jumps to End. 0x1C − 0x0C = 0x10: offset +16, four instructions ahead.
- `02:03` Case 3: j Loop goes from 0x18 back to 0x0C. 0x0C − 0x18 = −12, three instructions back: offsets can be negative.
- `02:15` Last episode mentioned position-independent code. Move the whole loop to 0x100C: every address changes, yet +16 and −12 stay exactly the same.
- `02:27` Had the instruction said "jump to 0x1C", the move would break it. Absolute addresses break when code moves.
- `02:36` Now to machine code. First beq x19, x10, End with offset +16: we did this last episode, so here's a quick replay.
- `02:46` Then fill in rs2 = x10, rs1 = x19, funct3 = 000 and opcode = 1100011, and we get 0x00A98863.
- `03:01` Next, j Loop. j is a pseudo-instruction for jal x0, Loop: the return address goes to x0, which simply discards it.
- `03:12` A J-type offset has 21 bits. −12 is negative, so in 21-bit two's complement the top 17 bits are all 1s and the last 4 bits are 0100.
- `03:24` As usual bit 0 isn't stored; the rest go to their slots in the order imm[20|10:1|11|19:12].
- `03:34` rd = x0 is 00000, and jal's opcode is 1101111.
- `03:42` The result is 0xFF5FF06F. The FF at the front and the FF in the middle both come from the negative offset's run of high 1s.
- `03:53` Line up S-type and B-type: both split the immediate into two pieces in the same places.
- `03:59` inst[30:25] is imm[10:5] in both, and inst[11:8] is imm[4:1] in both: identical meaning.
- `04:11` Only two bits change meaning. inst[31] is imm[11] in S-type but imm[12] in B-type, though it's always the sign bit;
- `04:21` inst[7] is imm[0] in S-type but imm[11] in B-type. When hardware builds the immediate, only these two bits need special handling.
- `04:32` Quick check: if a program has only 32-bit instructions, is inst[8] of every B-type instruction always 0?
- `04:41` Yes. Every offset is then a multiple of 4, so imm[1] is always 0, and imm[1] is exactly what inst[8] holds.
- `04:52` Offsets are in 2-byte units, so a branch can never move the PC by one byte. And with only 32-bit instructions, half of the encodable targets are unusable.
- `05:04` As we worked out last time, a B-type offset spans −4096 to +4094 bytes: about ±4 KiB, or 2^10 instructions either way.
- `05:17` If statements and loops are usually short, so that's plenty. But if far is more than 4 KiB away, beq x10, x0, far can't reach it.
- `05:27` The fix: negate the condition, and let the branch just hop over a j.
- `05:32` If x10 is 0, the bne isn't taken; j far runs and jumps far away.
- `05:39` If x10 isn't 0, the bne skips the j and carries on at next. Exactly what the original beq did.
- `05:47` j is J-type with a 21-bit offset: about ±1 MiB, or 2^18 instructions either way.
- `05:56` That's also why unconditional jumps use j rather than beq x0, x0: J-type drops rs1, rs2 and funct3, so its offset gets 8 more bits: 256 times the range.
- `06:11` Last episode we saw that auipc plus jalr can reach anywhere in the 32-bit address space. There's another pair too: lui plus jalr.
- `06:23` The absolute version first: lui loads the target's upper 20 bits, and jalr adds the lower 12 and jumps. The target is one fixed address.
- `06:34` jalr computes the target from the old ra while writing PC + 4 into ra, so one register serves as both the base and the return address.
- `06:44` The auipc version is PC-relative: ra = PC + (hi << 12). The target moves with the code, so it still works when the whole block moves.
- `06:56` This pair is exactly what the pseudo-instruction call expands to.
- `07:00` To jump without returning, set jalr's rd to x0, and hold the upper part in t1 so the return address in ra survives.
- `07:10` Careful: jalr's 12-bit immediate is sign-extended too. So how do we split hi and lo? It's the same question as for li.
- `07:20` Let's practice last episode's lui + addi on two examples from the notes. One thing first: for a constant between −2048 and 2047, li needs just one addi.
- `07:32` Example 1: li x10, 0x87654321. The upper 20 bits, 0x87654, go to lui; the lower 12 bits, 0x321, go to addi.
- `07:48` lui gives 0x87654000. The top bit of 0x321 is 0, so sign extension leaves it alone, and the sum is exactly 0x87654321.
- `08:02` While we're here, the machine code: lui is U-type with opcode 0110111 (auipc's is 0010111), giving 0x87654537; the addi is 0x32150513.
- `08:21` Example 2: li x10, 0xB0BACAFE. Same recipe: lui x10, 0xB0BAC, then addi x10, x10, 0xAFE?
- `08:35` The trouble is 0xAFE: its top bit is 1, so as a 12-bit two's complement number it's negative, and it's sign-extended to 0xFFFFFAFE.
- `08:47` 0xB0BAC000 + 0xFFFFFAFE = 0xB0BABAFE: the upper 20 bits come out 1 short!
- `09:00` Because 0xFFFFFAFE equals 0xAFE − 0x1000. Adding it adds 0xAFE and subtracts 0x1000, which takes exactly 1 off the upper 20 bits.
- `09:16` So add 1 to the upper 20 bits in advance: lui x10, 0xB0BAD. 0xB0BAD000 + 0xFFFFFAFE = 0xB0BACAFE. Correct.
- `09:32` The rule: if the top bit of the lower 12 (bit 11) is 1, add 1 to the upper 20 bits. As a formula: hi = (x + 0x800) >> 12.
- `09:45` The same rule splits hi and lo for the previous section's lui or auipc plus jalr. With auipc, x is the distance from the PC to the target.
- `09:59` Quick check: how many bits does li x5, 0x44331416 take once encoded?
- `10:07` 64 bits: li is a pseudo-instruction, and here it expands into two instructions, lui and addi.
- `10:16` Finally, two checklists for translating between assembly and machine code. First, assembly → binary; I* is the shift format from Episode 10.
- `10:26` In step 3, first turn ABI names into register numbers: s0 is x8, written 01000; t4 is x29, written 11101.
- `10:39` The reverse is Episode 10's disassembly, with its four steps on the right. Keep the 61C reference card handy.
- `10:47` Let's try it on a J-type: translate 0xFF5FF06F back. The opcode is 1101111: that's jal.
- `10:58` Split it as J-type: rd is 00000, so x0. Reassemble the immediate as imm[20|10:1|11|19:12], append the implicit 0, and get −12.
- `11:14` Put together: jal x0, −12. That's the j Loop we encoded earlier.
- `11:21` The notes also translate a whole file. The label main has no machine code, and the pseudo-instruction mv a0, a5 is really addi a0, a5, 0.
- `11:33` The last line, call printf, became a single jal: when the target is close enough, the toolchain shrinks auipc + jalr into one jal.

## 13-call-compile-assemble-link-load

- `00:06` Getting from a C file to a running program takes four steps.
- `00:12` Compiler, Assembler, Linker, Loader: put their first letters together and you get CALL.
- `00:18` The compiler translates C into assembly: exactly what we've been doing by hand in earlier episodes.
- `00:25` The compiler's output may use pseudo-instructions such as mv, li and j; the assembler expands them.
- `00:32` The assembler reads assembly code and produces an object file. Besides machine code, it holds information for linking and debugging.
- `00:41` Job one: expand pseudo-instructions into real instructions.
- `00:46` Job two: turn labels into offsets. But there's a snag: forward references.
- `00:52` When the assembler reaches bne, it hasn't seen Skip defined yet, so it can't tell how far to jump.
- `00:59` The fix: two passes. The first pass generates no machine code; it just records each label's address in the symbol table.
- `01:08` The second pass generates the machine code, now knowing where Skip is: offset = 0x08 − 0x00 = 8.
- `01:18` But some addresses can't be worked out in any number of passes: calling printf in another file, or taking the address of static data A.
- `01:26` Their final addresses aren't known until link time, so the assembler lists these holes in the relocation table: a to-do list for the linker.
- `01:36` So an object file holds a header, a text segment, a data segment, a relocation table, a symbol table and debugging information.
- `01:45` The linker combines several object files into one executable.
- `01:50` Step 1: concatenate the text segments, then append the data segments.
- `01:55` Step 2: with the segments laid out from 0x10000 up, every symbol has its final address. printf is at 0x10180.
- `02:06` Step 3: fill every hole in the relocation table. The jal at 0x10040 in foo must reach printf…
- `02:15` …and since jal is PC-relative, the offset filled in is 0x10180 − 0x10040 = 0x140.
- `02:27` Branches inside a file need no changes: PC-relative offsets stay correct when the whole block moves. That's the position independence from Episode 11.
- `02:36` By the way, modern systems often use dynamic linking, where libraries are linked in only when the program is loaded. What we've shown is static linking.
- `02:46` Finally, the operating system's loader actually gets the executable running.
- `02:51` It reads the header to learn how big the text and data segments are, then creates a new address space…
- `02:57` …copies the code and data into memory…
- `03:01` …puts the command-line arguments on the stack, initializes the registers, and points sp at the top of the stack…
- `03:08` …and finally jumps to a start-up routine, which calls main. The program is running!
- `03:14` We've now traveled the whole road: from C code to assembly, to machine code, to a program running in memory.
- `03:21` Registers, memory, branches, function calls, instruction encoding, compiling and linking: that's the big picture of RISC-V in CS61C.

## 14-life-of-hello-world

- `00:06` Last time we met the four steps of CALL. This time, let's follow one real program all the way through.
- `00:14` First, a quick check: after which step are all the machine code bits of these two instructions known?
- `00:20` Step one: the compiler translates the C code into assembly, hello.s.
- `00:26` Note that la, call, li and ret are pseudo-instructions, left for the assembler to expand.
- `00:33` Lines starting with a dot are directives: they produce no machine instructions, they tell the assembler how to lay out the object file.
- `00:41` .text says what follows goes in the text segment; .align 2 aligns it to 2² = 4 bytes.
- `00:49` .global (also spelled .globl) makes main a global symbol that other files can refer to.
- `00:55` Then we switch to the read-only data section, .rodata, again aligned to 4 bytes.
- `01:01` .string stores a null-terminated string; the labels str1 and str2 mark where each one starts.
- `01:09` Two other common directives aren't used here: .data switches to the data segment, and .word stores 32-bit words one after another.
- `01:18` Step two: the assembler produces the object file hello.o. It's binary: looked at directly, it's just a run of hex numbers.
- `01:27` Disassembling main: addresses within the module on the left, machine code in the middle, instructions on the right.
- `01:34` The pseudo-instructions are expanded. This listing is simplified: call became a single jalr.
- `01:42` But these five have immediates of 0, just placeholders: the assembler doesn't yet know where the data or printf will be.
- `01:50` The other instructions involve no addresses, so their machine code is final after assembly.
- `01:56` The symbol table lists this file's labels and their offsets within their segments; the debugger gdb uses it too.
- `02:03` main sits at offset 0 of the text segment and is global: that's what .global did.
- `02:09` Both strings are local data. The first is 12 bytes including its terminating 0, so the second starts at 0xc.
- `02:17` The relocation table is the linker's to-do list: one entry per placeholder.
- `02:22` The first two: the lui at 0x8 waits for the upper 20 bits of str1's address, the addi at 0xc for the lower 12.
- `02:31` Same for str2; the last entry, at 0x18, is the jalr waiting for printf's address.
- `02:40` Why can the assembler settle some addresses but not others? Because there are three kinds.
- `02:45` One: PC-relative jumps within the file, like beq, or jal to a local label. Wherever the code moves, the distance stays the same.
- `02:55` Two: addresses of static data, like str1 for la, or a global that lw reads. They're known only once all the files are put together.
- `03:05` Three: external functions like printf. It lives in another file, so the assembler can't even tell how far away it is.
- `03:13` The last two go into the relocation table. So jal sometimes needs editing, but B-type branches stay within the module and never do.
- `03:23` Step three: the linker combines hello.o, the start-up code and printf from the library into the executable a.out.
- `03:31` Where's printf? The linker searches the user's .o files first, then the libraries. A .a library is just a bundle of .o files.
- `03:40` Linking also makes separate compilation possible: change hello.c and only it gets recompiled, not the huge C library.
- `03:48` First the text segments are laid end to end from 0x10000: start-up code first, then main, and further on, printf.
- `03:57` The data segment follows the code: str1 lands at 0x20A10, str2 12 bytes later.
- `04:06` Every symbol now has its final address, and the linker updates the symbol table.
- `04:11` Then it works through the relocation table, filling each hole. First, every instruction gets its final address.
- `04:18` Start with str1 = 0x20A10. The low 12 bits, 0xA10, have their top bit set, so addi reads them as the negative number -1520.
- `04:31` So the upper 20 bits get an extra 1: 0x21. It's the same split li uses, from Episode 12.
- `04:38` 0x21 goes into lui's immediate field: the placeholder zeros become real address bits.
- `04:45` addi gets -1520, and both instructions are complete.
- `04:49` Likewise for str2: lui gets 0x21 again, addi gets -1508.
- `04:56` Finally, printf: it's at 0x10450, 0x288 bytes from the call.
- `05:03` jal reaches ±1 MiB, which is plenty, so the linker rewrites this as a single jal.
- `05:11` The other instructions are untouched. Add a header and debugging info, and a.out is done: every bit is now fixed.
- `05:20` Back to the quick check: add involves no addresses, so it's settled after assembly.
- `05:25` But jal targets fprintf, an external function in the stdio library, so it's settled only after linking.
- `05:33` What we just did is static linking: the library code is copied into a.out. The program is self-contained, but large.
- `05:41` When the library fixes a bug or a security hole, every program must be relinked and shipped again.
- `05:48` Dynamic linking keeps the library in its own file, such as libc.so, and links it in when the program is loaded.
- `05:55` Programs get smaller, and they can share one copy of the library in memory. Replace libc.so and they all upgrade.
- `06:03` The cost: linking overhead at run time, and a.out alone no longer runs. On balance, it's still worth it.
- `06:11` A bonus, not tested: instead of translating a program, we can hand it to an interpreter, another program that runs it directly.
- `06:19` Python is fully interpreted: easiest to write, slowest to run. Java compiles to bytecode, which is then interpreted, so it runs anywhere.
- `06:29` C compiles to machine code and is much faster. Machine code is the hardest to write, yet the easiest to "interpret": the hardware runs it directly.
- `06:39` Machine code can be interpreted in software too: Venus simulates RISC-V one instruction at a time, so you can step through it.
- `06:46` Each time Apple switched ISAs, software ran the programs built for the old one. The latest is Rosetta.
- `06:53` Interpreters are easier to write, debug and port; translated programs usually run 10 times faster or more, and keep the source private.
- `07:03` Putting it together: compile to assembly, assemble to machine code with placeholders, fill in the addresses when linking, then load and run.
- `07:12` The loader reads a.out into memory, the start-up code calls main, and Hello, world! appears.
- `07:19` It's the whole series in miniature: registers, memory, branches, functions, instruction encoding, and CALL.
- `07:27` From one line of printf to a string of settled bits: that's the road a program travels before it runs.
