## 03-memory-lw-sw

- `00:06` A processor has only thirty-two registers, but a real program has arrays,
- `00:10` structures and thousands upon thousands of variables.
- `00:14` Whatever doesn't fit in the registers has to live in memory.
- `00:18` RISC-V is what we call a load-store architecture, which means arithmetic instructions work only on registers,
- `00:25` and reaching memory takes special instructions.
- `00:29` A load copies data from memory into a register, and a store writes a register's value back out to memory.
- `00:37` You can picture memory as one enormous array of bytes, where every byte has its own number, called its address.
- `00:45` To keep the picture readable we draw four bytes per row, so the first row runs from 0x100 to 0x103,
- `00:52` and the next row starts at 0x104.
- `00:55` A word takes four bytes, so the addresses of neighboring words differ by four, not by one.
- `01:01` Word addresses are normally multiples of four, which is called alignment,
- `01:05` and a misaligned access can be slower or even fail outright.
- `01:10` How do we fit a thirty-two bit number, such as 0x12345678, into four bytes?
- `01:16` RISC-V uses what's called little-endian order, which puts the least significant byte at the smallest address.
- `01:24` So reading upward from 0x100, the bytes are seven eight, five six, three four and one two,
- `01:30` which looks like the number was stored backwards.
- `01:33` The good news is that loading or storing a whole word reassembles the number for you,
- `01:38` so you rarely need to think about byte order.
- `01:43` Now suppose memory holds the integer array A, which starts at address 0x100 and uses one word per element.
- `01:50` The address where the array begins is called the base address, and we'll keep it in the register s0.
- `01:57` The instruction lw stands for load word.
- `02:01` Take lw t0, 8(s0), which reads one word from the address s0 plus 8 and puts it into t0.
- `02:09` The offset, 8, plus the base address gives 0x108, and that is exactly where A[2] lives.
- `02:18` So in C, the element A[i] sits at a byte offset of four times i.
- `02:22` For example, A[3] is at offset 12, not 3, and mixing those two up is one of the most common mistakes in assembly.
- `02:32` The store instruction sw goes the other way and writes a register's value into memory.
- `02:38` Let's work through a complete example, where element three of the array A is set to h plus element one,
- `02:45` and h is kept in s1.
- `02:47` First we load element one into a register.
- `02:50` Next we add h, so t0 becomes ten plus twelve, which is twenty-two.
- `02:55` Finally sw writes that value back to element three,
- `02:59` and notice that sw lists the source register first and the memory address second.
- `03:05` In hexadecimal, twenty-two is 0x16, so with little-endian order the lowest address, 0x10C, holds the byte 0x16,
- `03:13` and the three bytes after it hold zero.
- `03:17` Besides whole words, RISC-V can also read and write a single byte, using the instructions lb, lbu, and sb.
- `03:24` When lb loads a byte into a thirty-two bit register, twenty-four extra bits are left over,
- `03:31` so what should they be filled with?
- `03:33` The answer is sign extension, which copies the top bit, the sign bit, into all the higher bits.
- `03:40` The top bit of 0xF3 is a one, so all twenty-four upper bits become ones, giving 0xFFFFFFF3.
- `03:46` As a signed number, 0xF3 is minus thirteen, and after extension it is still minus thirteen.
- `03:53` The unsigned version, lbu, always fills the upper bits with zeros, so the result is 243.
- `03:59` And sb goes the other way,
- `04:01` writing only the lowest eight bits of a register to memory and ignoring the other twenty-four.
- `04:09` Halfwords, which are sixteen bits, follow the same rules with lh, lhu, and sh.
- `04:15` And since lw already reads a full thirty-two bits, it needs no extension, which is why RV32 has no lwu.

## 07-function-calls

- `00:06` Calling a function takes six basic steps.
- `00:08` First we put the arguments where the function can get them, and then jump over to it.
- `00:13` The function sets up local storage for itself and runs its body.
- `00:17` Then it puts the return value in place, and finally jumps back to where it was called from.
- `00:24` Let's look at the simplest example, a is set to sum of a and b, where a is in s0 and b is in s1.
- `00:31` In step one we put the arguments into a0 and a1, and the return value will come back through a0 too.
- `00:39` The jal instruction first stores the address of the next instruction, PC plus four, into ra, and then jumps to sum,
- `00:47` which is why it is called jump and link.
- `00:51` The function computes its result and puts it into a0.
- `00:55` Then jr ra jumps back to the address that ra remembers, 0x100C, and execution carries on from there.
- `01:04` Why not jump back with a plain j?
- `01:07` Because sum can be called from many places, and only ra knows where this particular call should return to.
- `01:15` The instruction jr ra is shorthand for jalr x0, 0(ra), and it is often written ret.
- `01:23` Here is the trouble.
- `01:24` There is only one set of registers, and the caller and the function being called share them.
- `01:30` But f needs registers too, and if it overwrites a value the caller still needs, that data is quietly destroyed.
- `01:36` So everyone agreed on a set of rules, called the calling convention.
- `01:42` The registers t0 through t6 and a0 through a7, along with ra, are caller-saved,
- `01:47` which means the function being called may change them freely.
- `01:51` The caller has to save them first if it needs them afterwards.
- `01:55` The registers s0 through s11, and sp, are callee-saved, so if a function wants to use them,
- `02:01` it must save the old values first and restore them exactly before returning.
- `02:07` In other words, across a function call the saved registers are guaranteed to be unchanged,
- `02:12` while the temporary and argument registers are not.
- `02:15` So where do we keep those old values?
- `02:18` The answer is the stack in memory.
- `02:21` A program's memory is roughly divided into blocks, which are the code, the static data, the heap, and,
- `02:27` at high addresses, the stack.
- `02:29` The stack grows downward from high addresses toward low ones, and sp, the stack pointer, points to the top of the stack,
- `02:37` which is the lowest address currently in use.
- `02:40` Let's zoom in.
- `02:42` Suppose a function needs to save two registers, ra and s0.
- `02:46` To push, we first subtract eight from sp, making room for two words.
- `02:52` Then we use sw to store the registers, with ra at sp plus four, and s0 at sp plus zero.
- `03:00` The function can now change ra and s0 freely.
- `03:03` Before returning, we pop in exactly the opposite order, using lw to get the old values back,
- `03:10` and then adding to sp to give the space back.
- `03:14` Now sp is back where it started, and the registers have their old values.
- `03:19` The data we stored doesn't need clearing, since it just no longer belongs to anyone.
- `03:25` Finally, a complete example, in which sumSquare calls another function, mult.
- `03:30` When it is called, the argument x, which is three, is in a0, the argument y, which is five, is in a1,
- `03:37` and ra holds the caller's return address.
- `03:39` Since sumSquare itself calls mult with jal, and jal overwrites ra, it has to save ra first,
- `03:45` or it could never get back to its caller.
- `03:48` It must also save y on the stack, because a1 is about to be used to pass x, and a1 is caller-saved,
- `03:54` so mult might change it.

## 08-recursion-and-stack-frames

- `00:06` In episode seven we used jal and jr ra, but RISC-V really has only two unconditional jump instructions.

- `00:36` so its address comes from a register.
- `00:39` Every other jump is a pseudo-instruction.
- `00:42` The j, jr, and ret instructions write the return address into x0, which throws it away,
- `00:50` while a jal with no rd links into ra.

## 09-formats-r-i-s

## 11-formats-b-u-j

- `00:06` A conditional branch compares two registers, rs1 and rs2, and also needs a jump target, and since it writes no register,
- `00:14` it has no rd.
- `00:15` But the target address itself is thirty-two bits, which can't possibly fit inside a thirty-two bit instruction.
- `00:23` So what do we do?
- `00:24` Notice that branches usually jump only a short way,
- `00:27` since an if or a loop body is typically a few to a few dozen instructions.
- `00:32` So we encode only the offset relative to the current PC, which is called PC-relative addressing.
- `00:39` RISC-V leaves room for sixteen-bit compressed instructions, so instruction addresses are always multiples of two,
- `00:46` and the lowest bit of the offset is always zero, which we don't need to store.
- `00:51` So twelve bits can represent a thirteen-bit offset, with a range of about four kibibytes either way,
- `00:57` or roughly a thousand instructions each way.
- `01:00` There is another benefit, which is that if the whole block of code moves elsewhere in memory,
- `01:05` the branch offsets need no change at all.
- `01:08` This is called position-independent code.
- `01:12` The B format is laid out almost like the S format.
- `01:15` The fields rs1, rs2, funct3, and opcode are in their old places, and the immediate is split into two pieces.
- `01:22` But the order of the immediate's bits is scrambled, with bit twelve at the very top of the instruction,
- `01:29` and bit eleven moved to the end of the right-hand piece.
- `01:33` This is to reuse the wiring of the S format.
- `01:36` Bits ten to five and bits four to one are in exactly the same places as in S, and the sign bit is always bit thirty-one.
- `01:45` Let's encode beq x19, x10, End.
- `01:48` End is four instructions ahead, so the offset is sixteen bytes.
- `01:52` Sixteen as a thirteen-bit binary number is zero, zero zero zero zero, zero zero zero one, zero zero zero zero.
- `02:01` The lowest bit isn't stored, and the other bits go into their prescribed places.
- `02:07` The registers are as usual, rs2 is x10 and rs1 is x19, the funct3 of beq is zero zero zero,
- `02:16` and the branch opcode is one one zero zero zero one one.
- `02:21` So the final machine code is 0x00A98863.
- `02:27` A twelve-bit immediate holds only small constants.
- `02:30` So how do we get a thirty-two bit constant, like 0xDEADBEEF, into a register?
- `02:36` The U format has just rd and a twenty-bit immediate, and the lui instruction, short for load upper immediate,
- `02:43` uses this format.
- `02:45` The instruction lui t0, 0xDEADB puts the twenty-bit immediate into the upper twenty bits of t0,
- `02:52` and clears the lower twelve bits to zero.
- `02:57` Can we then add the low twelve bits, 0xEEF, with an addi?
- `03:01` Careful, because the immediate of addi is signed.
- `03:05` The top bit of 0xEEF is a one, so as a twelve-bit two's complement number it means minus two hundred seventy-three,
- `03:13` and it gets sign-extended to 0xFFFFFEEF.
- `03:17` The sum comes out as 0xDEADAEEF, so one has been borrowed from the upper twenty bits.
- `03:23` The fix is, when the top bit of the low twelve bits is one, to add one to the upper twenty bits first, and write lui t0,
- `03:33` 0xDEADC.
- `03:34` Luckily we don't need to work this out by hand, because the pseudo-instruction li t0,
- `03:40` 0xDEADBEEF is expanded by the assembler into these two instructions.
- `03:45` Another U-format instruction is auipc, which shifts the immediate left by twelve bits and adds it to the PC,
- `03:52` to work out an address far from the current position.
- `03:57` The jal instruction needs only rd and an offset, so the J format gives all the remaining twenty bits to the immediate.
- `04:04` As before, the unit is two bytes and the lowest bit isn't stored.
- `04:09` So the offset is twenty-one bits, with a range of about one mebibyte either way, enough to cover most function calls.
- `04:16` The bit order is scrambled again, so that as many bits as possible line up with the I format and the U format,
- `04:23` and the sign bit still stays at bit thirty-one.
- `04:27` What if the target is farther away?
- `04:29` The jalr instruction is an I format, which jumps to rs1 plus the immediate, and stores PC plus four into rd.
- `04:37` Together with auipc computing the upper twenty bits first, we can jump anywhere in the thirty-two bit address space,
- `04:45` and that is how the pseudo-instruction call is expanded.
- `04:50` Now let's put all six RV32I formats together.
- `04:53` The positions of rs1, rs2, rd, and the opcode never change, and only the arrangement of the immediate varies.
- `05:01` And the sign bit of the immediate is always bit thirty-one,
- `05:05` so the hardware can start sign extension before it even knows the instruction type.

- `07:30` That is the same problem as li.
- `07:33` Let's practice last episode's lui plus addi with two problems from the notes.

- `08:22` while auipc is zero zero one zero one one one.

- `09:35` we add one to the upper twenty bits first.
- `09:38` As a formula, hi equals x plus 0x800, shifted right by twelve.
- `09:42` Splitting hi and lo for lui or auipc with jalr in the last section follows the same rule, and with auipc,
- `09:50` x is the difference between the target address and the PC.

## 13-call-compile-assemble-link-load

- `00:06` Going from a C file to a running program takes four steps.
- `00:09` They are the Compiler, the Assembler, the Linker, and the Loader, and their initials spell CALL.
- `00:15` The compiler translates C into assembly, which is what we have been doing by hand in the last few episodes.
- `00:22` The assembly a compiler outputs can contain pseudo-instructions, such as mv, li, and j,
- `00:28` leaving the work of expanding them to the assembler.
- `00:33` The assembler reads assembly code and produces an object file,
- `00:37` which holds the machine code plus information needed for linking and debugging.
- `00:42` Its first job is to expand pseudo-instructions into real instructions.
- `00:48` The second job is converting labels into offsets, but there is a catch, the forward reference.
- `00:53` When the assembler reads the bne, it hasn't seen the definition of Skip yet, so it doesn't know how far to jump.
- `01:01` The fix is to scan twice.
- `01:02` The first pass generates no machine code, and only records each label's address in the symbol table.
- `01:09` On the second pass we generate the machine code, and now the address of Skip is known, so the offset is 0x08 minus 0x00,
- `01:18` which is eight.
- `01:20` But some addresses can't be worked out however many times we scan, such as calling printf in another file,
- `01:27` or taking the address of static data A.
- `01:29` Their final addresses aren't known until link time,
- `01:32` so the assembler records these holes to be filled in the relocation table, and leaves them to the linker.
- `01:40` So an object file contains a header, the code segment, the data segment, the relocation table, the symbol table,
- `01:46` and debugging information.
- `01:49` The linker puts several object files together into one executable.
- `01:53` Step one is to join the code segments of the files end to end, and then put the data segments after them.
- `02:00` Step two.
- `02:01` Once the positions of the segments are fixed, with the code starting at 0x10000,
- `02:08` the final address of every symbol is fixed too, for example printf at 0x10180.
- `02:15` Step three is to fill in the holes one by one, using the relocation table.
- `02:22` The jal at 0x10040 in foo has to jump to printf.
- `02:27` Since jal uses a PC-relative offset, what goes in is 0x10180 minus 0x10040, which is 0x140.
- `02:37` Branches inside a file need no change at all, because PC-relative offsets stay correct when the whole block moves,
- `02:44` which is exactly the position independence from episode eleven.
- `02:48` By the way, modern systems often use dynamic linking, where libraries are linked in only when the program is loaded,
- `02:56` but what we describe here is static linking.
- `03:00` Finally, the loader in the operating system actually gets the executable running.
- `03:05` It first reads the header, to learn how big the code and data segments are,
- `03:09` and creates a new address space for the program.
- `03:13` Then it copies the code and data into memory, puts the command-line arguments on the stack, initializes the registers,
- `03:20` and points sp at the top of the stack.
- `03:22` Finally it jumps to the startup routine, which calls main, and the program starts running!
- `03:29` That completes the whole journey, from C code to assembly, to machine code, and then to a program running in memory.
- `03:37` Registers, memory, branches, function calls, instruction encoding, compiling and linking,
- `03:43` this is the whole picture of the RISC-V part of CS61C.

## 14-life-of-hello-world

- `00:27` Notice that la, call, li, and ret are all pseudo-instructions, left for the assembler to expand.
